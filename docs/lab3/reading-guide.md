# Лабораторная работа 3 — что почитать

Этот файл — не сценарий защиты (он в `defense-script.md` рядом), а
объяснение «на понимание»: что это вообще такое, зачем так сделано и чем
отличается от того, что было раньше.

---

## 1. Структура программы целиком

```
cmd/
  utility-bills/main.go    — точка входа веб-сервера
  migrate/main.go          — отдельная утилита миграций БД (запускается
                              вручную, не частью сервера)

internal/
  app/
    config/config.go       — чтение config/config.toml (хост/порт сервера)
    dsn/dsn.go              — сборка строки подключения к PostgreSQL
                              из переменных окружения
    ds/                     — модели (структуры данных = таблицы БД
                              + сериализаторы для API)
      utility.go             Utility, FullUtilitySerializer,
                              UtilityListItem, UtilityFeedItem
      user.go                User
      like.go                Like
    repository/             — вся работа с БД и MinIO, единственный слой,
                              которому разрешено видеть *gorm.DB
      repository.go           подключение к Postgres + MinIO
      env.go                  сборка настроек из переменных окружения
      utility.go               методы для SSR и общие (список, лента,
                              черновик, публикация, удаление)
      user.go                 регистрация пользователя
      like.go                 лайки
      upload.go               загрузка файлов в MinIO
    handler/                — обработка HTTP-запросов, вызов репозитория,
                              формирование ответа (HTML или JSON)
      handler.go               общая часть: структура Handler, регистрация
                              маршрутов, функция-синглтон CurrentUserID
      utility.go               HTML-страницы лаб 1-2 (плитка/лента/добавление)
      api_utility.go           JSON REST API лабы 3 — услуги
      api_user.go              JSON REST API лабы 3 — пользователи
  pkg/
    app.go                  — сборка приложения (конфиг + роутер + хендлер)
                              и запуск сервера

templates/                 — html/template-шаблоны трёх HTML-страниц
resources/
  styles/, img/, video/    — CSS и файлы-заглушки по умолчанию

docs/lab2/, docs/lab3/     — документация и материалы для защиты
```

**Принцип:** зависимости идут только в одну сторону —
`handler → repository → ds`. Хендлер никогда не пишет SQL сам,
репозиторий никогда не знает про HTTP (`gin.Context`), модели (`ds`) не
знают вообще ни про что — это просто описание данных.

## 2. Что изменилось относительно лабы 1

Лаба 1 была чисто HTML: сервер рендерил готовые страницы
(`html/template`), данные лежали в срезе Go-структур в памяти — без БД
вообще. Три GET-метода, без JavaScript.

## 3. Что изменилось относительно лабы 2

Лаба 2 добавила PostgreSQL через GORM: три таблицы (`utilities`, `likes`,
`users`), 6 методов (5 через ORM, 1 через сырой SQL — специально для
практики прямого SQL в обход ORM). Маршруты были вложены под
`/utilities/...`, формы — обычные HTML с `GET`/`POST` (браузер не умеет
нативно `PUT`/`DELETE`).

## 4. Что принесла лаба 3 — подробно

### 4.1. Появился настоящий REST API, отдельно от HTML-страниц

До этого всё приложение было ориентировано на браузер: пользователь
кликает кнопку → браузер шлёт форму → сервер отдаёт готовую HTML-страницу.
Это SSR (Server-Side Rendering) — то, что делали лабы 1-2, и эти страницы
**никуда не делись**, работают как раньше (`/`, `/utilities/feed`,
`/utilities/draft`).

Лаба 3 добавила **параллельный** интерфейс — JSON API под `/api/...`.
Разница принципиальная:

| | HTML-страницы (лабы 1-2) | REST API (лаба 3) |
|---|---|---|
| Кто клиент | браузер человека | программа (Postman, будущий React) |
| Что отдаёт сервер | готовая HTML-страница | чистые данные в формате JSON |
| Методы HTTP | только GET и POST (ограничение форм) | GET, POST, PUT, DELETE — honest REST |
| id в запросе | из скрытого поля формы или URL | из URL (`/api/utilities/:id`) |
| Тело запроса | `application/x-www-form-urlencoded` | JSON (`Content-Type: application/json`) или `multipart/form-data` для файлов |

Зачем два интерфейса сразу? Потому что курс поэтапно собирает систему:
сейчас данные читает и браузер (через SSR), и Postman (через API), а
начиная с 5-й лабы данные REST API начнёт читать React-фронтенд — тогда
HTML-страницы станут не нужны, но сейчас убирать их рано.

### 4.2. HTTP-методы стали значить то, что должны (REST)

Раньше **все** действия шли через `POST`, потому что HTML-форма не умеет
по-другому. REST API использует методы по смыслу:

- `GET` — только читать, ничего не меняет
- `POST /api/utilities` — создать новую запись
- `PUT /api/utilities/:id` — изменить существующую (публикация)
- `DELETE /api/utilities/:id` — удалить (логически)

Это не просто вкусовщина: по методу запроса сразу понятно, какое у него
намерение, и это даёт возможность, например, кешировать `GET`-запросы или
безопасно повторять их — чего нельзя делать с `POST`.

### 4.3. Загрузка файлов стала настоящей

В лабе 2 поля выбора файла на странице «Добавление» были декоративными —
методичка прямо требовала их не сохранять. В лабе 3 через API файлы
**реально** загружаются:

1. Клиент шлёт `POST /api/utilities` с `Content-Type: multipart/form-data`
   — тело запроса состоит из частей: текстовое поле `name` и файлы
   `image`/`video`.
2. Сервер читает файл **не доверяя** его заголовку — определяет реальный
   тип по первым 512 байтам содержимого (`http.DetectContentType`).
   Это защита: клиент мог написать в заголовке «это картинка», а на
   самом деле прислать исполняемый файл.
3. Файл загружается в MinIO под именем на латинице:
   `utility-<id>-image.webp`, `utility-<id>-video.mp4` — имя строится из
   id только что созданной записи, поэтому коллизий не бывает.
4. Ссылка на файл в MinIO (`http://localhost:9000/utilities/...`)
   сохраняется в колонке `image_url`/`video_url` в БД — сам файл лежит в
   объектном хранилище, в базе только ссылка.

### 4.4. Вложенная сериализация

Простой пример: в базе `Utility` хранит только `creator_id` — число,
внешний ключ. Но клиенту неудобно получать голое число — ему нужно имя
автора, модератор он или нет и т.д. «Вложенная сериализация» — это когда
при ответе API GORM сам «дотягивает» связанную запись и вкладывает её
целиком внутрь ответа:

```go
type FullUtilitySerializer struct {
    Utility
    Creator User `json:"creator"`
}
```

В запросе к БД это делается через `Preload("Creator")` — GORM выполняет
дополнительный `SELECT` по таблице `users` и подставляет результат в
поле `Creator`. Итоговый JSON выглядит так:

```json
{
  "id": 1,
  "name": "Электроэнергия",
  "creator": { "id": 1, "login": "user", "isModerator": false }
}
```

Вместо голого `"creatorId": 1` клиент сразу получает всё нужное про
автора одним запросом — не нужно делать второй запрос «а кто это 1?».

По той же логике сделаны `UtilityListItem` (добавляет вычисляемое поле
`isMine`) и `UtilityFeedItem` (добавляет `liked`) — это тоже
сериализаторы: берут базовую модель и достраивают её дополнительными
данными под конкретный ответ, не трогая саму таблицу в БД.

### 4.5. Функция-синглтон вместо голой константы

И в лабе 2, и в лабе 3 нет настоящей авторизации — «текущий пользователь»
везде один и тот же (появится в лабе 4 через JWT/сессии). Раньше это было
прямой константой, разбросанной по коду. В лабе 3 это намеренно
обёрнуто в функцию:

```go
func CurrentUserID() uint {
    return currentCreatorID
}
```

Разница небольшая по объёму кода, но важная по смыслу: когда в лабе 4
появится реальная авторизация, поменяется **только тело этой одной
функции** (будет читать ID из токена/куки), а все 6 мест в коде, которые
её вызывают, трогать не придётся вообще. Это и называется «синглтон» —
единая точка доступа к значению, которое логически должно быть одно на
всё приложение.

### 4.6. Ограничение смены статуса

Требование методички: «Статусы нельзя менять с любого на любой». У нас
это реализовано не проверкой в коде (`if status == ...`), а прямо в
условии SQL-запроса:

```go
r.db.Model(&ds.Utility{}).
    Where("id = ? AND status = ?", id, ds.StatusDraft).
    Updates(...)
```

Если услуга не в статусе `draft` — строка просто не найдётся, `UPDATE`
не затронет ни одной записи, и сервер вернёт 404. Опубликованную услугу
нельзя «переопубликовать» или вернуть в черновик — физически невозможно,
потому что такой `UPDATE` ничего не найдёт по условию.

### 4.7. Удаление — через ORM, а не сырой SQL (отличие от лабы 2!)

Важный нюанс, в котором легко ошибиться: в лабе 2 метод удаления **прямо
требовалось** написать через сырой SQL (`db.Exec("UPDATE ...")`) — это
было специальное упражнение «сделать то же самое в обход ORM». В лабе 3
требование обратное: «Взаимодействие с БД через ORM» касается **всех**
методов API без исключения. Поэтому `DeleteUtilityOwned` (используется
только в `/api/...`) написан через построитель запросов GORM:

```go
r.db.Model(&ds.Utility{}).
    Where("id = ? AND creator_id = ?", id, creatorID).
    Update("status", ds.StatusDeleted)
```

А старый `DeleteUtility` на сыром SQL (используется HTML-страницей
плитки из лабы 2) никуда не делся — он просто для другого интерфейса,
где сырой SQL был частью задания.

## 5. Теория к контрольным вопросам лабы 3

**Веб-сервис** — программа, предоставляющая функциональность другим
программам по сети через стандартизированный интерфейс (чаще всего HTTP).
Отличие от веб-сервера: веб-сервер (nginx, Apache) отдаёт статику и
проксирует запросы, веб-сервис содержит бизнес-логику.

**REST (Representational State Transfer)** — архитектурный стиль, а не
протокол. Ключевые принципы:
- **Stateless** — сервер не хранит состояние клиента между запросами,
  каждый запрос самодостаточен (поэтому до появления токена-сессии в
  лабе 4 пользователь передаётся «константой»)
- Единообразный интерфейс — ресурсы адресуются URL (`/utilities/:id`),
  действия над ними — HTTP-методами (`GET`/`POST`/`PUT`/`DELETE`)
- Представление ресурса (JSON) отделено от самого ресурса (строки в БД)

**RPC (Remote Procedure Call)** — альтернативный стиль, где клиент
вызывает именованную процедуру на сервере (`doSomething(args)`), а не
оперирует ресурсами по URL. REST моделирует данные как существительные
(`/utilities`), RPC — как глаголы-действия. Пример RPC-подобного API:
gRPC, JSON-RPC.

**Заголовки HTTP** — метаданные запроса/ответа, не часть тела.
Используемые у нас: `Content-Type` (что за данные в теле — `application/json`
или `multipart/form-data`). В REST важны также `Accept`
(что клиент готов принять) и коды статуса (200 OK, 201 Created,
404 Not Found, 409 Conflict — все используются в нашем API).

**Методы HTTP**, которые реально значат:
- `GET` — безопасный (не меняет состояние) и идемпотентный (повторный
  вызов даёт тот же результат)
- `POST` — не идемпотентен (повторный `POST /api/utilities` создаст
  вторую запись)
- `PUT` — идемпотентен: повторный `PUT` с теми же данными даст тот же
  результат (у нас — публикация, повторный вызов второй раз просто не
  найдёт черновик и вернёт 404, а не создаст дубль)
- `DELETE` — идемпотентен: удалить уже удалённое — не ошибка в духе REST
  (хотя у нас возвращает 404 при повторном вызове, что тоже
  валидный REST-подход)

**Версии HTTP:**
- HTTP/1.0 — одно соединение на запрос
- HTTP/1.1 — постоянные соединения (`keep-alive`), конвейеризация
- HTTP/2 — мультиплексирование нескольких запросов в одном соединении,
  бинарный протокол вместо текстового
- HTTP/3 — поверх QUIC (UDP вместо TCP), меньше задержек на
  установление соединения

**HTTPS** — HTTP поверх TLS/SSL: шифрование канала, подтверждение
подлинности сервера сертификатом. В разработке используем обычный HTTP
(`localhost`), в проде — обязательно HTTPS.

**OSI/ISO** — эталонная 7-уровневая модель сетевого взаимодействия:
физический → канальный → сетевой → транспортный → сеансовый →
представления → прикладной. HTTP живёт на прикладном уровне (7),
поверх TCP (транспортный, уровень 4), поверх IP (сетевой, уровень 3).
Модель TCP/IP на практике проще — 4 уровня вместо 7, но при ответе на
контрольный вопрос обычно просят именно 7-уровневую OSI.

## 6. Если спросят «а почему два отдельных POST на создание/публикацию,
а не один большой метод»

Потому что это два принципиально разных действия с разным набором
обязательных полей: создание требует только название (+ опционально
файлы), публикация требует описание и оба поля по теме. Разделение на
`draft → published` — это классический паттерн «сохранить черновик,
потом дозаполнить и отправить», знакомый по любому интерфейсу
(email-клиенты, CMS, формы заявок). Плюс это прямое требование
методички — у создателя именно «два разных метода», а не один
универсальный `PATCH`.
