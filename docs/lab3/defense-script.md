# Защита лабораторной работы 3 — как показывать

## Подготовка
1. Docker Desktop запущен, `docker ps` показывает `utilities-postgres`,
   `utilities-minio`, `utilities-adminer` живыми.
2. Приложение собрано и запущено: `.\utility-bills.exe` (порт 8080).
3. В Postman: **File → Import** → `docs/lab3/postman-collection.json`.
4. Перед показом у вас НЕ должно быть черновика (иначе запрос 2 даст 500,
   т.к. `CreateUtilityDraft` не проверяет дубль) — проверить в Adminer:
   `SELECT id FROM utilities WHERE status='draft';` и удалить/опубликовать,
   если есть лишний.

## Порядок показа (скриншоты 1-10 — по одному на запрос)

Выполняйте запросы коллекции **строго по номерам** — так совпадёт с
методичкой:

1. **GET список** — уже видно `isMine` у каждой услуги.
2. **POST добавить** — в форме `formdata` руками прикрепите файл в поля
   `image` и `video` (кнопка «Select Files» у строки). Ответ содержит `id`
   нового черновика — **скопируйте его** в переменную коллекции `draftId`
   (клик по коллекции → Variables → `draftId` → Current value).
3. **GET черновик** — виден тот же id, статус `draft`.
4. **PUT опубликовать** — использует `{{draftId}}` из переменной. Ответ
   `"услуга опубликована"`.
5. **GET лента без id** — первая опубликованная услуга.
6. **GET лента `?next=true`** — следующая после id=1.
7. **POST лайк** — ответ содержит обновлённый `likesCount`.
8. **DELETE удалить** — удаляет ту же услугу (`{{draftId}}`), что
   публиковали в п.4 — наглядно: только что опубликовали, теперь удаляем.
9. **POST регистрация** — если `newuser` уже существует (повторный
   прогон), поменяйте `login` в теле на другой, иначе 409.
10. **GET услуга подробно** — здесь же объясняете вложенную сериализацию:
    в ответе есть поле `creator` с данными пользователя, а не только его id.

## Скриншоты 11-13 — select в БД

После запроса 2 (добавление) и запроса 4 (публикация) — в Adminer
выполните `SELECT * FROM utilities WHERE id = <draftId>;` и снимите
результат до/после публикации. После запроса 8 (удаление) — ещё раз
select, статус должен быть `deleted`.

## На словах — что объяснять по каждому методу

- **GET список/лента** — фильтрация и признаки `isMine`/`liked`
  вычисляются на бэкенде, а не на клиенте.
- **POST добавление** — `multipart/form-data`, файлы реально загружаются
  в MinIO под латинскими именами (`utility-<id>-image.webp`), не просто
  текстовая ссылка.
- **PUT публикация** — смена статуса только `draft → published`, условие
  `WHERE status = 'draft'` в запросе не даёт опубликовать уже
  опубликованное или удалённое — то самое «нельзя менять статус с любого
  на любой».
- **DELETE** — проверяет `creator_id`, чужую услугу не удалить (покажите
  попытку удалить услугу не своего пользователя → 404).
- **POST like** — идемпотентно: повторная установка уже стоящего лайка не
  создаёт дубль (уникальный индекс в БД).

## Важно: диаграмма классов

Методичка (раздел «Лабораторная 3») **явно требует** диаграмму классов
для этой лабы: «Диаграмма классов с детализацией бэкенда (домены методов
по url с интерфейсами, перечислить все методы, модели, таблицы БД, 4
страницы фронтенда)». Если вы считаете, что её не нужно показывать
вместе с лабой 3 — уточните у преподавателя, потому что по тексту
методички это отдельное обязательное требование именно этой лабы, не
следующей.
